# NoName Agent Harness · 架构草案

> v0.2 · 2026-08-16 · 状态：概念设计，未实现
>
> 本版吸收了对 DeepSeek Harness、SQLite、mem0、Zep/Graphiti 与 LangMem 的调研，重点收敛四个问题：可溯源记忆、完整运行时、交互式账本、多模型与品味卡片。

## 0. 核心修正

上一版把「上下文包」称为核心抽象，但还不够精确。现在明确区分四个层次：

1. **证据 Evidence**：原始会话、工具输入输出、文件 diff、模型响应。不可变、可回放，是事实来源。
2. **记忆 Memory**：从证据中抽取的事实、决策、任务态和引用。可版本化、可失效，但不硬删除。
3. **品味 Taste**：跨项目延续的态度与选择倾向，拥有独立的来源、审核和作用域。
4. **上下文包 Context Package**：在某次会话启动时组装出来的可携带视图，不是数据库，也不是唯一真相。

因此：**压缩可以有损，证据不能丢；上下文可以裁剪，溯源不能断。**

## 1. 总体运行图

```
用户指令
   │
   ▼
Session Log ── append-only 事件流 ──▶ Evidence Store
   │                                      │
   │                                      ▼
   │                              Memory Extractor
   │                                      │
   │                              候选记忆 + source span
   │                                      │
   │                                      ▼
   │                         Review / Policy / Versioning
   │                                      │
   ▼                                      ▼
Router ──▶ Context Assembly ◀──── Memory + Taste Projections
   │              │
   │              ▼
   │       Model Adapter / Model Recipe
   │              │
   ▼              ▼
Agent Loop ──▶ Tool Registry ──▶ Execution World
   │              │                    │
   └──────────────┴──── Ledger ◀────────┘
```

## 2. 记忆原则

### 2.1 证据优先，而不是摘要优先

上下文压缩器的输出不能成为唯一记录。每一个长期记忆候选都必须带：

- `source_event_id`：来自哪一个会话事件；
- `source_span`：原文中的字符区间、消息区间或文件 diff 区间；
- `source_artifact`：文件、git commit、工具结果或外部来源；
- `extractor_run_id`：由哪个模型、哪次提取运行产生；
- `extraction_reason`：为什么认为它值得进入长期层；
- `confidence`：模型的置信度只是参考，不能代替审核；
- `status`：`candidate / pending_review / accepted / rejected / superseded / retired`。

「摘要」是导航索引，不是原文的替代品。无法回到证据的长期记忆，不得进入法典或品味层。

### 2.2 记忆写入是提案，不是事实

模型可以提出记忆，但不能默默改变长期状态。默认写入流程：

```
证据产生
  → 提取候选
  → 去重 / 冲突检测
  → 用户审核队列
  → 接受、编辑、拒绝或延后
  → 生成新版本
  → 可回滚、可追踪
```

用户明确说「记住这件事」时，可以降低审核摩擦，但仍保留来源和版本记录。对法典、用户品味、跨项目人格等高影响内容，必须明确确认。

### 2.3 上下文包是投影

上下文包由以下内容按预算组装：

- 与当前任务相关的法典片段；
- 当前任务态；
- 必要的证据引用和最近事件；
- 经审核的品味层；
- 本次任务提示和多 agent 注入；
- 模型与工具能力说明。

不同模型、不同任务可以得到不同的包，但都指向同一份证据和版本化记忆。包本身可以丢弃和重建，事实来源不会因此改变。

## 3. 记忆、运行时与账本的边界

| 组件 | 负责什么 | 不负责什么 |
|---|---|---|
| Session Log | 记录发生过的事件 | 不决定事件意义 |
| Evidence Store | 保存原始内容与可回放对象 | 不直接塞满模型上下文 |
| Memory Service | 提取、检索、版本、失效、溯源 | 不替用户批准高影响记忆 |
| Taste Service | 管理跨项目态度、画像与卡片 | 不改变事实正确性 |
| Context Assembler | 为当前模型生成上下文视图 | 不修改长期数据 |
| Ledger | 展示因果、决策、成本和状态变化 | 不取代原始日志 |
| Agent Loop | 驱动模型、工具和状态转移 | 不绕过权限与审批 |

## 4. 运行时骨架

NoName 借鉴 DeepSeek Harness 的「一切能力都可替换」和事件溯源思想，但把会话格式、迁移和长期数据稳定性作为长期主义约束。详细设计见 [runtime-architecture.md](runtime-architecture.md)。

必须存在的稳定接口：

- **Model Adapter**：统一不同模型的消息、工具调用、流式输出、计费和能力声明；
- **Model Recipe**：定义任务角色与模型组合，而不是把模型名称散落在业务逻辑中；
- **Tool Registry**：分离模型可见 schema 与宿主执行实现；
- **Session Log**：append-only、可回放，模型可见内容必须可由日志重建；
- **Agent Loop**：明确的状态机，不把整个 agent 行为藏在一个巨大函数里；
- **Policy / Approval**：工具能调用不等于可以免审批调用；
- **Plugin Runtime**：插件通过稳定 seam 贡献能力，所有副作用可卸载。

## 5. 记忆技术路线

当前不把 mem0、Zep 或 LangMem 当作完整解决方案：

- 以 SQLite 作为本地唯一事实来源，可配合 FTS5 和 sqlite-vec；
- 借 Zep/Graphiti 的 episode、双时序、失效而非删除、事实到证据血缘；
- 借 LangMem 的 semantic/profile/collection/episodic/procedural 分层；
- 借 mem0 的记忆管理器操作思想，但将 `DELETE` 改为版本化失效；
- 检索、提取、审核和上下文投影由 NoName 自己定义。

详细表结构语义见 [memory-model.md](memory-model.md)。

## 6. 多模型与模型配方

模型切换不是把一个字符串换成另一个字符串，而是选择一个可审计的 **Model Recipe**。配方包含：

- 任务类型：探索、规划、实现、审查、记忆提取、视觉表达等；
- 角色链：例如 `planner → worker → critic`；
- 每个角色的模型适配器、上下文预算、工具权限和停止条件；
- 成本、延迟、质量和隐私偏好；
- 失败回退模型；
- 用户自定义覆盖。

默认配方只提供建议，不锁死用户。每次选择都记录在账本中，用户可以回答「这次推荐是否合适」，让路由规则逐步变得可解释。

## 7. 品味层与品味卡片

品味至少分成两条来源不同的轨道：

1. **Authored Taste（自述品味）**：用户主动写下、明确确认或长期维护的态度，具有最高权威；
2. **Adopted Taste（采纳品味）**：模型从一次回答、作品或选择中提炼出的令人眼前一亮的倾向，经用户选择后跨项目延续，但不伪装成用户亲自说过的话。

品味只影响态度层：排序、取舍、表达方式、探索方向和模型配方建议。它不能直接覆盖事实、权限、任务要求，也不应被用作「生成质量」的隐式评分器。

品味卡片是品味的可视化复核界面，不是事实数据库的新格式：

- 一张卡对应一组相近的品味证据；
- 卡片显示时间范围、来源数量、代表性原文、适用作用域、冲突和置信度；
- 生成图片只是该组品味的视觉隐喻，不能代替文字证据；
- 卡片可以接受、编辑、拆分、合并、暂停或退休；
- 卡片按确定性队列出现，抽卡是复核体验，不使用随机稀有度或赌博式奖励；
- 新旧品味可以并存，冲突可被看见，而不是强行合并成一个「永远正确的你」。

详细设计见 [taste-cards.md](taste-cards.md)。

## 8. 交互式账本

账本不是开发者日志的换皮，而是回答三类问题的交互界面：

1. **发生了什么？** 事件时间线：用户输入、模型决定、工具执行、文件变更、记忆候选；
2. **为什么这样做？** 因果链：路由、模型配方、审批、法典引用、品味影响；
3. **现在的状态从哪里来？** 版本 diff：当前法典、品味卡和任务态分别由哪些证据投影而来。

账本默认显示少量关键节点，点击后逐级展开原始证据。它应像一张可缩放的地图，而不是把所有 token 倾倒在屏幕上。详细设计见 [ledger.md](ledger.md)。

## 9. 插件原则

借鉴 DeepSeek Harness 的依赖注入、可逆 effect、能力接缝和作用域隔离，但补上 NoName 的长期约束：

- 插件可以替换实现，不可以绕过证据、审批和账本；
- 插件声明 manifest、能力、权限、数据迁移和版本兼容范围；
- 插件副作用必须绑定生命周期，停止或更新时可逆；
- agent 级插件不能偷偷注册进程级全局状态；
- 核心接口保持迁移承诺，插件能力可以快速演化；
- 插件是被验证过的能力结晶，不是用户探索新领域的默认入口。

参考：[DeepSeek Harness architecture](https://github.com/deepseek-ai/DeepSeek-Harness/blob/HEAD/docs/architecture.md)。

## 10. 用户审核是产品体验的一部分

记忆污染不是弹窗可以解决的技术问题，而是用户是否理解「批准意味着什么」的问题。界面必须明确说明：

- 这条记忆将影响哪些项目；
- 它来自哪段证据；
- 接受后会改变什么；
- 可以在哪里撤回或退休；
- 不审核就不会进入长期层。

产品不应把审核伪装成无意义的确认按钮。审核应该是短小、可解释、可批量但不盲目的判断工作。

## 11. 当前风险与开放问题

本轮暂不展开论文级问题，只保留方向：

- 如何测量「完整证据 + 不同上下文投影」对任务连续性的影响；
- 如何在不丢证据的前提下控制检索和上下文成本；
- 如何避免提取器把模型臆测写成事实；
- 如何验证品味只影响态度，而不污染事实和任务完成质量；
- 如何评估视觉化品味卡片是否帮助复核，而不是制造新的偏见；
- 什么时候应该把一个涌现工作流结晶成插件；
- 稳定会话格式和数据库迁移如何跨多年演进。

这些问题留到下一轮，不在本次假装给出答案。

## 12. 验证顺序

1. 先验证 append-only 证据、source span、记忆候选和人工审核；
2. 再验证上下文包投影与跨模型接管；
3. 再加入模型配方、工具注册和账本因果视图；
4. 再加入品味双轨与卡片复核；
5. 最后评估插件结晶和多模态视觉层。

每一步验证一个长期主义假设，不以做出一个看起来完整的 demo 为目标。
