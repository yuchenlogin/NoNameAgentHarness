# NoName Agent Harness · 架构草案

> v0.1 · 2026-08-16 · 状态：概念设计，未实现
>
> 本文把 [vision.md](vision.md) 里的理念翻译成机制，并补充那些
> 「只有经历过全流程 agent 设计才会知道」的实现细节。
> 每一节尽量说明：这个机制解决什么问题、为什么放在这里、失败的代价是什么。

## 0. 总览

```
用户指令 ──▶ 路由 Router（继续 / 重生 / 模型选择 / 批准）
              │
              ▼
组装 Assembly（拼接，从不原地修改）
  = 法典(只读) + 任务态 + 任务提示 + 注入提示(带来源) + 品味
              │
              ▼
模型 Model（可热插拔；写作模型 / 审查模型可以不同）
              │
              ▼
执行（基础工具：文件 / 命令 / web / 子 agent；受沙箱与审批约束）
              │
              ▼
账本 Ledger（每次工具调用都记账：diff、hash、成本）
              │
              ▼
压缩 Compaction（一次版本化提交；产物必须通过「重生测试」）
```

## 1. 上下文包 Context Package

### 1.1 为什么是「包」，而不是「提示词」

提示词是一次性的、模型私有格式的、写完了就没了的东西。上下文包要求相反：
它是**模型无关、可版本化、prompt-native 的文本资产**。
任何能读它的模型都能接管这份工作——这是热插拔成立的前提。

### 1.2 四层结构

| 层 | 内容 | 变化速度 | 谁写 |
|---|---|---|---|
| 法典 Canon | 项目目标、约束、非妥协项、决策与理由（ADR） | 慢，像宪法 | 模型提议，人批准 |
| 任务态 Task | 当前目标、开放问题、阻塞、下一步 | 快，每次压缩重写 | 模型 |
| 指针 Provenance | 指向档案/文件/git 版本，而不是复制内容 | 慢 | 自动 |
| 品味 Taste | 你的追求、态度、审美：例子与判断 | 慢，随人成长 | 人为主，模型观察为辅 |

### 1.3 保真原则：充分 + 可溯源

「准确传递」是不可能的——压缩必然有损。正确的目标改成：

- **充分**：新模型凭这份包能继续任务而不跑偏；
- **可溯源**：被压缩掉的任何细节，都能经指针回到档案（会话存档、git diff、原始文件）。

所以规则是：**记忆存「决策 + 理由 + 指针」，细节留在档案**。
记忆负责让新会话不迷路，档案负责让旧细节不被遗忘。

### 1.4 版本化与账本

每次压缩是一次提交：有版本号、有 diff、可回看、可回滚。账本只增不改。
「上下文永远是组装出来的，从不原地编辑」——这条规则让一切注入可审计。

### 1.5 增长与遗忘

账本只增不改，长期会变重——这是真实风险（见 §13）。对策：

a) 压缩产出的是**增量 diff**，稳定知识只留引用，不重复复制；
b) 法典支持**日落机制**：过期决策可被标记 deprecated
（永不删除，只标注「何时为何失效」）。

## 2. 组装流水线 Assembly

### 2.1 拼接顺序与优先级

新上下文 = 按序拼接：

1. 法典（只读引用，按需检索相关章节，不是全文倾倒）
2. 任务态（最近一次压缩的产物）
3. 本次任务提示
4. 注入提示（子 agent 总结、协作指令）——**拼接，不修改 1–3**
5. 品味层（压缩成「判断与例子」，预算很小）

顺序即优先级：法典 > 注入 > 任务提示里的即时指令（这条本身可配置）。

### 2.2 注入的溯源与命名空间

每条注入必须带来源元数据：哪个子 agent、哪次运行、时间、schema 版本。
冲突**可见而不被覆盖**：父会话看到的是
「reviewer-agent 的意见与法典 v12 冲突，请裁决」，
而不是静默的文本拼贴。

### 2.3 预算分配

token 预算要在五部分之间显式分配
（例如法典 35% / 任务态 30% / 注入 20% / 品味 5% / 系统与工具 10%，可调）。
「法典按需检索」是路由器的问题，不是组装的问题：先取与当前任务相关的章节。

## 3. 路由 Router

### 3.1 继续 vs 重生

决策信号（权重可插拔、用户可调）：

- **阶段边界**（首选时机）：一个子目标完成。压缩应发生在「编译时刻」而不是被迫截断；
- **饱和压力**：上下文接近上限或有效信息密度下降；
- **模型切换**：下一阶段需要另一种模型；
- **用户指令**：显式「开新会话」。

必须加**迟滞**（hysteresis）：不能在「继续/重生」之间来回抖动。
路由决策必须记入账本：为什么切、带着哪个版本的包、理由是什么。

### 3.2 模型路由与热插拔

- 任务特征 → 模型选择：规则本身可以是模型或启发式，**用户可调整映射表**；
- **双模型模式**（今天就能用的热插拔）：一个模型负责写，另一个模型负责审查——
  审查独立于写作，能力互补，这是「按擅长分工」的最朴素实现；
- 代价要诚实：不同模型对同一份法典的理解深度不同，保真度必须度量（§12）。

### 3.3 路由决策的审计

每次路由决策（继续/重生/换模型/审批放行）都写入账本，附理由。
用户应该能回看「为什么当时换成了模型 B」。

## 4. 压缩 Compaction

### 4.1 时机

原则：**在阶段边界主动压缩，而不是在饱和时被动截断**。
饱和时压缩 = 在模型思路的中途打断，损失最大。
路由应该在开始一个阶段之前估算「这个阶段是否放得进剩余预算」，
放不进就先压缩再开始。

### 4.2 算法轮廓

1. 模型回读本阶段会话，产出「决策清单 + 任务态更新 + 待办」；
2. 与现有法典做 diff：只有**新增或变化**的部分进入法典；
3. 指针自动记录本阶段的产物位置（文件、git hash）；
4. 产出**候选包 vN+1**，人类可以审阅（默认展示 diff，而不是全文）；
5. 通过「重生测试」后才提交为 vN+1。

### 4.3 重生测试

用候选包 + 新任务提示，在**全新上下文**（可以换一个模型）里接管任务，
回答一组固定问题：目标是什么？已决定了什么？下一步是什么？哪些不能碰？
回答质量就是保真度。这是整个系统最重要的自我检验，也是最有论文潜力的度量（§12、§14）。

## 5. 规范即记忆 Spec-native

### 5.1 spec 状态机

proposed → approved → in-progress → done → archived。
spec 条目就是法典的正文；「写 spec」和「维护记忆」是同一件事，
所以模型有内生动力去做。

### 5.2 ADR = 决策记忆

每条重要决策用 ADR 形式记录：背景 / 决策 / 理由 / 后果。
这是「记忆传递准确」里「理由」部分的标准格式——
换模型后，理由比结论更能防跑偏。

### 5.3 对账 pass

定期让模型对照**账本与代码事实**核查 spec：spec 说要做 A，代码里 A 在哪？
找不到就报告漂移。这是规范内化后最重要的质量保证：
法典的权威来自与现实的持续对账，不来自书写。

### 5.4 仪式感是法典的一条

「本项目需要多少仪式感」本身是法典里的一条，由你决定。
NoName 不预设模板——你不填表，你只调一个旋钮。

## 6. 品味层 Taste

### 6.1 形式：例子与判断，不是形容词

「简洁、大气」是无用的；有用的是：

- 判断记录：`保留了 X / 否决了 Y，因为 Z`；
- 参考例子：你认可的界面、文案、命名；
- 「足够好」标准：什么情况下停手（对完美主义倾向的人是真实的工程参数）。

### 6.2 采集

- **显式询问**（罕见）：高后果的品味决策（命名、品牌、对外发布）；
- **观察**（主要）：你批准了什么、否决了什么、改了什么——这些行为就是品味数据；
- **定期确认**：隔一段时间让你复核品味条目，防陈旧。

### 6.3 风险：过拟合成一个「你」的漫画

agent 可能把你固化成一幅漫画：永远推同一种方案、永远引用你的旧判断。
对策：品味与法典一样版本化、可编辑；
agent 应偶尔给出「偏离你品味」的选项，并说明理由。

### 6.4 跨模型一致性

品味在上下文包里，因此换模型不换人。这可以变成一个测试：
换模型后，在新模型给出的一组候选里，你选中的是否仍是同一类（§12.4）。

## 7. 多智能体 Multi-agent

### 7.1 上下文分离 + 结构化回传

子 agent 在隔离上下文里工作，回传的不是聊天记录，而是结构化小结：
结果 / 产物位置 / 开放问题 / 置信度 / **「不要做什么」**。
父级不读子级全量日志（会重新撑爆上下文），只读回传；需要细节时经指针下钻。

### 7.2 注入不修改

子 agent 的总结以「注入」形式拼进父会话（§2.2）——这正是理念里的 1.3：
拼接而不修改，冲突可见，来源可溯。

### 7.3 一个任务一个上下文

子 agent 的内部上下文在任务结束后即结束；只有回传与指针存活。
这防止「上下文分离后总结」退化成「上下文合并后混乱」。

## 8. 核心 vs 涌现

| 必须留在核心（不可谈判） | 可以交给模型涌现 | 插件的位置 |
|---|---|---|
| 沙箱与权限（物理保证，不是模型决定） | 工作流、启发式、编排 | 可选的能力结晶，不是默认入口 |
| 审批栈（高后果操作的闸门） | 计划：先做什么、后做什么 | 流程被证明稳定且高频时，可以固化 |
| 账本（事实：改了什么、跑了什么、花了多少） | 领域知识 | |
| 基础工具执行（文件 / 命令 / web / 子 agent） | | |
| 路由骨架（策略可插拔，但骨架存在） | | |

判断标准只有一条：**这条保证在模型出错（甚至被提示注入）时还成立吗？**
不成立就留在核心。安全是物理保证问题，不是能力问题——模型再强也不能把这一列删掉。

## 9. 账本与可观测性 Ledger

- **事实 vs 叙述**：模型会讲故事，工具会留凭证。信任凭证，不信任叙述。
  账本记录每次工具调用的参数、结果、git hash、diff、成本；
- **重放**：任何历史状态可以重放，因为指针与版本都在；
- **成本**：按任务类别记账，路由才有依据（哪类任务用哪个模型最划算）。

## 10. 工具核心 Tools

### 10.1 最小集

文件操作 / 命令执行 / web 搜索与抓取 / 子 agent 派生 / 沙箱。
「基础工具 + 品味」是赌注：让更多能力涌现，而不是安装。

### 10.2 可以调用 vs 可以不经批准调用

模型「可以调用」某工具，不等于「可以不经批准」调用。
权限策略把每个工具 × 参数范围分成三档：自动 / 批准一次 / 永远批准。

### 10.3 不可逆操作分类学

对外发布、删除、花钱、发消息、跨出工作区写文件……这些永远走审批，
无论模型多强、无论它怎么说。这一条属于 §8 的核心。

## 11. UI 原则

信息层级（高→低）：

1. **作品**——正在被创造的东西；
2. **意图**——agent 此刻打算做什么（一句话）；
3. **账本状态**——记忆版本、当前模型、上下文年龄、最近一次压缩；
4. **控制**——罕见的高后果操作，按需出现。

视觉：极简、克制、一个强调色；文字优先；留白是信息。
界面的职责是让你「看见」，不是让你「操作很多」。

## 12. 评估 Evaluation

1. **重生测试**（§4.3）：换模型接管成功率——保真度的第一度量；
2. **金任务集**：一组真实项目任务，记录「继续 / 重生后」完成度差异；
3. **跨模型保真度矩阵**：同一包 × 不同模型 × 不同任务类；
4. **品味一致性**：换模型后你的选择分布是否一致；
5. **涌现 vs 结晶**：同一任务，模型现场合成 vs 插件固化，比成本与质量——
   这直接检验 §8 的赌注。

## 13. 已知风险与失败模式

1. **记忆污染**：坏决策一旦进入法典就会复利。→ 法典写入必经批准；重生测试不过不提交。
2. **法典漂移**：spec 与现实脱节。→ 对账 pass（§5.3）。
3. **批准疲劳**：要批准的东西太多，人开始机械点「同意」。→ 三档权限 + 同类操作批处理 + 批准理由可读。
4. **账本变成新的上下文窗口**：记忆越积越重。→ 增量 diff + 按需检索 + 日落机制（§1.5）。
5. **品味过拟合**（§6.3）。
6. **路由抖动**：继续/重生来回切。→ 迟滞 + 决策入账可审计（§3.3）。
7. **agent 成为记忆的囚徒**：法典太僵硬，创新被自己的历史否决。→ 定期法典复审；「日落」旧决策。

## 14. 开放问题（研究议程）

1. **保真度度量**：重生测试如何标准化？能否做成公开基准（模型无关的上下文 ABI）？
2. **遗忘**：账本何时该遗忘而非标记 deprecated？遗忘与保真的理论关系？
3. **品味的形式化**：例子与判断如何结构化？品味在多大程度上跨模型可迁移？
4. **路由默认策略**：对「普通开发者」最优的默认权重是什么？路由决策如何向人解释？
5. **对账的自动化程度**：spec vs 代码的对账能多自动？
6. **涌现 vs 结晶的边界**：什么时候模型现场合成的成本会低于插件固化？怎么测？
7. **包的大小与预算**：各层预算如何随项目类型自适应？

## 15. 验证顺序（不急，但方向是清晰的）

概念阶段只做一件事：把上面的问题想清楚，并把「重生测试」定义到可以实施。
实现从最窄的垂直切片开始——单个项目、单模型、只有法典与任务态两层、人工路由；
然后逐层加：注入（多智能体）、品味层、模型路由、对账。
每一步都在验证一个假设，而不是在堆功能。demo 可以等，假设不可以不验证。
